# Syntax Analysis Phase

The **Syntax Analysis** phase is the second stage of the compiler. It receives the token stream from the lexical analyzer and checks whether the tokens follow the grammar rules defined in `parser.y`.

This phase is implemented using **GNU Bison**, which generates an **LALR(1) bottom-up parser**.

The parser in your project also performs:

* **Production Rule Tracing**
* **Parse Tree Construction**
* **SHIFT / REDUCE / ACCEPT Action Trace**
* **Syntax Error Detection**



---

# Main Files

| File           | Purpose                    |
| -------------- | -------------------------- |
| `parser.y`     | Grammar + semantic actions |
| `parser.tab.c` | Generated parser source    |
| `parser.tab.h` | Token declarations         |

---

# Why Syntax Analysis Is Needed

The lexer only recognizes valid words/symbols.

Example token stream:

```text id="m4a6x1"
ASYNC FUNCTION IDENTIFIER LPAREN IDENTIFIER COMMA IDENTIFIER RPAREN
```

But lexer cannot tell if this sequence forms a valid function declaration.

Syntax analysis verifies structural correctness such as:

* Is `if` followed by condition?
* Are brackets balanced?
* Is `return` inside valid statement form?
* Are parameters written correctly?
* Are expressions grammatically legal?

---

# Parsing Method Used: LALR(1)

# Full Form

**LALR(1)** = **Look Ahead LR Parser with 1 Lookahead Token**

---

# Meaning

| Term                 | Meaning                              |
| -------------------- | ------------------------------------ |
| Left-to-right        | Reads tokens from left to right      |
| Rightmost derivation | Builds reverse derivation bottom-up  |
| Lookahead 1          | Uses one next token to decide action |

---

# Why Used in Your Project

* Efficient parser tables
* Handles programming language grammars well
* Faster than recursive descent for this grammar
* Automatically generated by Bison
* Detects syntax conflicts using lookahead token

---

# Example of Lookahead Use

Input:

```text id="x7e2n0"
IDENTIFIER (
```

Parser waits for next token to decide:

```text id="y5f7u9"
IDENTIFIER()       → function call
IDENTIFIER(expr)   → call with arguments
IDENTIFIER + ...   → another expression
```

---

# Grammar Rules (CFG)

Your syntax phase is based on **Context Free Grammar**.

Example rules:

```text id="h8m1r6"
program     → stmt_list
stmt_list   → stmt_list stmt
stmt        → async_func_decl
stmt        → var_decl
stmt        → expr_stmt
```

---

# Function Grammar

```text id="m0n7q4"
async_func_decl →
async function IDENTIFIER ( param_list ) { func_body }
```

Recognizes:

```javascript id="t9v3p7"
async function uploadFile(files, fileData) { ... }
```

---

# Conditional Grammar

```text id="n3r1z6"
if_stmt → if ( if_cond ) { throw_stmt }
```

Recognizes:

```javascript id="r7k8m0"
if (!fileData.name || !fileData.size) {
   throw new Error(...)
}
```

---

# Expression Grammar

Supports:

```text id="v6u3a2"
files.find(...)
files.push(newFile)
a === b
5 * 1024 * 1024
```

---

# Production Rule Trace

Whenever parser reduces symbols into a non-terminal, your project prints production rules.

Example:

```text id="b5q2s1"
param_list → IDENTIFIER , IDENTIFIER
const_decl → const IDENTIFIER = expr
if_stmt → if ( if_cond ) { throw_stmt }
program → stmt_list
```

---

# Why Important?

Shows exactly how parser derives the final program from grammar rules.

Useful in viva and debugging.

---

# Parse Tree

Your parser prints tree representation of recognized syntax.

Example:

```text id="d7m0x4"
├─ AsyncFunctionDeclaration
  └─ name: "uploadFile"

├─ ParamList
  └─ param: "files"
  └─ param: "fileData"
```

Inside body:

```text id="q8w1e7"
├─ IfStatement
  └─ condition: "!x.y || !x.z"

├─ VariableDeclaration (const)
  └─ name: "MAX_SIZE"

├─ ReturnStatement
  └─ value: "newFile"
```

---

# Why Parse Tree Matters

It shows hierarchy:

```text id="x4f2l0"
Function
 ├─ Parameters
 ├─ Body
 │   ├─ If
 │   ├─ Const
 │   └─ Return
```

This structure is later used for semantic analysis.

# Parser Actions

Bison parser works using stack operations.

---

# SHIFT

Push current token onto stack.

Example:

```text id="j3v9k5"
SHIFT async
SHIFT function
SHIFT uploadFile
```

Meaning parser is collecting symbols.

---

# REDUCE

When RHS matches grammar rule, reduce to LHS.

Example:

```text id="c0q7n2"
IDENTIFIER , IDENTIFIER
↓
param_list
```

Trace:

```text id="z2u8s1"
REDUCE param_list → IDENTIFIER , IDENTIFIER
```

---

# ACCEPT

Final successful parse.

```text id="g1f0r3"
ACCEPT program
```

---

# Example Full Flow

Input:

```javascript id="m8r2p6"
async function uploadFile(files, fileData)
```

Trace:

```text id="a6x5q2"
SHIFT async
SHIFT function
SHIFT uploadFile
SHIFT (
SHIFT files
SHIFT ,
SHIFT fileData
REDUCE param_list
REDUCE async_func_decl
```

---

# Stack Concept

Parser internally maintains stack:

```text id="v9e6k1"
[async]
[async function]
[async function IDENTIFIER]
...
[async_func_decl]
```

This is why it is called **bottom-up parsing**.
