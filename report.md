## Abstract

This paper presents the design and implementation of JS2TS, a source-to-source compiler that translates a subset of JavaScript into fully typed TypeScript. The compiler is implemented in C using Flex for lexical analysis and GNU Bison for syntax analysis, and performs type inference through a post-parse Abstract Syntax Tree (AST) walk. Unlike template-based approaches, the compiler derives all type annotations structurally from the parsed program — inferring object shapes from object literals, array element types from method usage patterns, and function return types from variable declarations. The system handles syntax errors with recovery and multi-error reporting. Experimental results on three representative JavaScript programs demonstrate correct TypeScript generation with accurate type annotations.

---

## I. Introduction

TypeScript has become the dominant typed superset of JavaScript in modern software development. However, large codebases written in JavaScript require significant manual effort to migrate to TypeScript. Automated tools that can infer types and generate typed TypeScript from untyped JavaScript reduce this burden.

This project implements a four-phase compiler pipeline — lexical analysis, syntax analysis, semantic analysis, and code generation — that processes JavaScript source and emits equivalent TypeScript with inferred type annotations. The compiler is built as an academic exercise in compiler design, demonstrating the application of formal language theory to a practical translation problem.

The key contribution of this work is the shift from hardcoded pattern matching to a general grammar-driven approach. The grammar describes JavaScript constructs structurally, the parser builds an AST for any valid input, and the semantic pass derives types from what the program actually does rather than from a lookup table keyed on function names.

## III. Phase 1 — Lexical Analysis

The lexer is implemented in Flex. It reads the JavaScript source character by character and produces a stream of tokens consumed by the parser.

### A. Token Classes

The lexer recognises six token classes:

1. **Keywords** — `async`, `function`, `const`, `let`, `if`, `else`, `return`, `throw`, `new`, `true`, `false`, `null`
2. **Operators** — `===`, `!==`, `<=`, `>=`, `||`, `&&`, `=>`, `=`, `-=`, `+=`, `*=`, `!`, `+`, `-`, `*`, `/`, `%`
3. **Punctuation** — `. , ; : ( ) { } [ ]`
4. **String literals** — `"([^"\\]|\\.)*"` — stored in `yylval.str`
5. **Number literals** — `[0-9]+(\.[0-9]+)?` — stored in `yylval.str`
6. **Identifiers** — `[a-zA-Z_$][a-zA-Z0-9_$]*` — stored in `yylval.str`

### B. Ignored Input

Whitespace, single-line comments (`//`), and block comments (`/* */`) are silently consumed. Unrecognised characters are skipped.

### C. Design Decisions

Keywords are listed before the identifier rule so that `async` returns `ASYNC` rather than `IDENTIFIER`. Longer operator patterns (`===`) precede shorter ones (`=`) to ensure correct matching. The `%option yylineno` directive enables automatic line number tracking used in error reporting.

## IV. Phase 2 — Syntax Analysis

### A. Parsing Method

The parser is generated by GNU Bison using the LALR(1) algorithm. LALR(1) parsers read input left-to-right, construct a rightmost derivation in reverse (bottom-up), and use one lookahead token to resolve shift/reduce decisions. This is well-suited to programming language grammars and is the method used by most production compilers.

### B. Grammar Design

The grammar is general — it describes JavaScript constructs structurally rather than encoding specific token sequences. The expression sub-grammar implements a full precedence hierarchy:

```
expr → assign_expr → or_expr → and_expr → eq_expr
     → rel_expr → add_expr → mul_expr → unary_expr
     → postfix_expr → primary_expr
```

This allows any valid JavaScript expression to be parsed without enumerating specific patterns. Key grammar rules are shown in Table I.

**Table I. Selected Grammar Productions**

| Non-terminal | Production |
|---|---|
| `func_decl` | `ASYNC FUNCTION IDENTIFIER ( param_list ) block` |
| `var_decl` | `CONST IDENTIFIER = expr ;` |
| `if_stmt` | `IF ( expr ) block [ ELSE block ]` |
| `postfix_expr` | `postfix_expr . IDENTIFIER ( arg_list )` |
| `arrow_func` | `IDENTIFIER => assign_expr` |
| `object_literal` | `{ prop_list }` |

### C. Abstract Syntax Tree

Every grammar rule constructs an AST node. The AST is a tagged union of `Node` structs with the following fields:

- `kind` — node type (enum `NodeKind`)
- `sval` — string value (identifier name, operator, literal text)
- `ival` — integer flag (async flag, const/let flag, boolean value)
- `left`, `right`, `extra` — child nodes
- `list` — linked list of child nodes (arguments, parameters, statements, properties)

The AST persists in memory through all subsequent phases.

### D. Error Handling

The directive `%define parse.error verbose` instructs Bison to generate descriptive error messages from its parse tables, e.g.:

```
syntax error, unexpected ASSIGN, expecting IDENTIFIER
```

Error recovery rules allow parsing to continue after a bad statement:

```bison
stmt : error SEMICOLON { $$ = NULL; yyerrok; }
     | error RBRACE    { $$ = NULL; yyerrok; }
```

All errors are collected with line numbers and reported together after parsing. If any errors exist, code generation is suppressed.

### E. Conflict Resolution

Two inherent JavaScript ambiguities produce grammar conflicts:

1. **Dangling else** — resolved with `%prec LOWER_THAN_ELSE` on the no-else rule. Bison defaults to shift, binding `else` to the nearest `if`.
2. **Arrow function body** — `x => expr` where `expr` could greedily consume binary operators. Resolved with `%prec ARROW` (lowest precedence) so the arrow body reduces before consuming outer operators.

## V. Phase 3 — Semantic Analysis

Semantic analysis is a post-parse AST walk implemented in `infer_program()`. It populates a symbol table and a type registry used by code generation.

### A. Type Inference Strategy

Type inference is driven entirely by structural patterns in the AST. No function names are hardcoded.

**Object type inference.** When a `const newX = { ... }` declaration is found, the variable name is used to derive a type name (`newUser` → `User`, `newFile` → `FileRecord`), and the object literal's properties are walked to infer property types (Table II).

**Table II. Property Value Type Inference**

| Property value | Inferred TypeScript type |
|---|---|
| `true` / `false` | `boolean` |
| String literal | `string` |
| Number literal | `number` |
| `Date.now()` | `number` |
| `new Date().toISOString()` | `string` |
| Arithmetic expression | `number` |
| Member access on string field | `string` (heuristic) |

**Array parameter inference.** If a parameter appears as the receiver of `.find()`, `.filter()`, `.push()`, or `.map()`, it is marked as an array. The element type is derived from the parameter name by stripping the plural suffix: `users` → `User[]`, `products` → `Product[]`.

**Input parameter inference.** Parameters not identified as arrays are treated as input objects. The type name is derived from the parameter name: `userData` → strip `Data` → `User` → append `Input` → `UserInput`.

**Return type inference.** The function body is scanned for `const newX = { ... }`. The derived type name is wrapped in `Promise<>`: `newUser` → `Promise<User>`.

### B. Syntax Directed Definitions (SDD)

The SDD specifies the attributes computed for each production:

| Production | Attribute | Value |
|---|---|---|
| `func_decl → async function ID(params) block` | `ID.type` | `async function(...): Promise<T>` |
| `var_decl → const ID = object_literal` | `ID.type` | `derive_type_name(ID.lexval)` |
| `var_decl → let ID = []` | `ID.type` | `ElemType[]` |
| `prop → ID : expr` | `prop.type` | `prop_val_type(expr)` |
| `expr → NUMBER` | `expr.type` | `number` |
| `expr → STRING` | `expr.type` | `string` |
| `eq_expr → e1 === e2` | `expr.type` | `boolean` |
| `add_expr → e1 + e2` | `expr.type` | `number` |
| `arrow_func → ID => expr` | `param.type` | element type of receiver array |

### C. Syntax Directed Translation (SDT)

The SDT specifies the actions executed during the semantic pass:

| Production | Action |
|---|---|
| `func_decl` | `infer_param_types(node)` → `var_set(name, sig, "global")` |
| `const ID = object_literal` | `register_object_type(type_name, obj_node)` → `var_set(ID, type_name, scope)` |
| `let ID = []` | `var_set(ID, "__let_array__", "global")` |
| `prop → ID : expr` | `type_add_prop(typedef, key, prop_val_type(expr))` |

### D. Symbol Table

The symbol table is a flat array of `VarEntry` structs (`name`, `type`, `scope`). Lookup matches on both name and scope to prevent cross-scope collisions. The table is printed after semantic analysis as shown in Table III.

**Table III. Symbol Table — input.js**

| Identifier | Type | Scope |
|---|---|---|
| `newUser` | `User` | `registerUser` |
| `users` | `User[]` | `registerUser` |
| `userData` | `UserInput` | `registerUser` |
| `registerUser` | `async function(...): Promise<User>` | `global` |

### E. Semantic Error Checks

| Condition | Error |
|---|---|
| Function has no parameters | Cannot infer types |
| No `const new* = {...}` in body | Return type unknown |
| Property value unresolvable | Property type unknown |

## VI. Phase 4 — Code Generation

Code generation walks the AST and emits TypeScript. The output is derived from the tree structure and the symbol table — not from pre-written templates.

### A. Emission Order

1. **Type aliases** — from the type registry (`emit_type_aliases`)
2. **Function declaration** — signature from symbol table, body from AST (`emit_func`)
3. **Top-level declarations** — `let` arrays with inferred element types (`emit_top_let`)

### B. Expression Emission

`emit_expr()` recursively emits any expression node. The notable special case is `.find()` / `.filter()` / `.map()` calls: the arrow function argument is annotated with the array's element type:

```typescript
// emitted by emit_expr for users.find(u => ...)
users.find((u: User) => u.email === userData.email)
```

The element type is obtained by looking up the array variable in the symbol table and stripping `[]`.

### C. Results

Table IV shows the type annotations generated for each input.

**Table IV. Generated Type Annotations**

## VII. Parse Trace

After successful compilation, the compiler writes a parse trace to a file (`trace_input1.txt`, etc.) by walking the AST a second time with `write_trace()`. The trace shows the AST structure, the symbol table, and a phase summary. This is generated from the same AST used for code generation — no separate tracing infrastructure is needed.

## VIII. Comparison with Prior Approach

The original implementation used hardcoded grammar rules and a `func_mode` variable:

```c
if (strcmp($3, "registerUser") == 0) func_mode = 1;
else if (strcmp($3, "uploadFile") == 0) func_mode = 2;
```

Code generation selected a pre-written TypeScript template based on `func_mode`. This approach failed for any function name not in the list and could not handle variations in input structure.

The revised compiler eliminates all hardcoding. Table V summarises the differences.

**Table V. Old vs New Compiler**

| Aspect | Old | New |
|---|---|---|
| Grammar | Hardcoded token sequences | General structural rules |
| Type inference | Lookup table by function name | AST walk, pattern-based |
| Code generation | Pre-written `fprintf` templates | Recursive AST emission |
| Unknown function name | No output | Fully handled |
| Error reporting | First error only | All errors with line numbers |
| AST | Not built | Full in-memory tree |

---

## IX. Conclusion

This paper presented JS2TS, a four-phase source-to-source compiler that translates JavaScript to TypeScript using Flex, Bison, and C. The compiler builds a general-purpose AST, infers types structurally from the parsed program, and emits TypeScript by walking the tree. The approach generalises beyond the three test inputs and handles syntax errors with recovery and descriptive reporting.

Future work could extend the grammar to cover additional JavaScript constructs (classes, destructuring, template literals), implement a proper type checker that validates inferred types against usage, and support multi-file compilation.
